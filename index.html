Saryom · architecture notebook · Nov 2026

How Saryom fits together

Saryom is one React app in front of an API gateway and eleven Spring Boot services. Each service owns one slice of the neighbourhood (buy and sell, chat, lending, local services, meetups, lost and found, housing, jobs) and its own Postgres schema. Services never call each other directly. They announce what happened as events on a message broker, and whoever cares listens. Everything runs on free tiers, and as of 21 November every request is traced into Grafana Cloud.

02 · Event flow

Who announces what, and who listens

Eight services publish, three consume. Notification-service listens to almost everything because nearly every event means someone should get a push or an email. Pick a service to see only the topics it touches.

TopicnotificationuserchatWhat the listener does
One sale, three reactions, zero direct calls.

When a seller marks an item sold, listing-service publishes listing.sold once. User-service adds one to the seller's sales count, chat-service closes every pending offer on that item, and notification-service sends the seller a congratulations push. Listing-service does not know any of them exist. Adding a fourth reaction later means a new consumer, and no change to listing-service.

A two-hop chain: following people.

User-service consumes listing.created, looks up who follows that seller, and publishes seller.listed. Notification-service turns that into pushes. The service that knows about follows owns the fan-out, so listing-service stays ignorant of the social graph. User-service also hears lending.returned and lostfound.resolved, which open a two-way review between the people involved, the same way a sale does.

03 · One request, end to end

What happens when a buyer makes an offer

This is the busiest path in the app: authentication, a write, an event, a live WebSocket push and a phone notification, all from one tap.

  1. The browser sends POST /api/chats/{threadId}/offers with the Firebase ID token it got at sign-in.
  2. The gateway's AuthenticationGatewayFilter deletes any X-User-Id the client sent, verifies the token, and forwards the request with a trusted X-User-Id. It keeps the token too.
  3. Chat-service verifies the token again (defense in depth), checks the caller is in the thread, marks any earlier pending offer as superseded, and saves the new offer plus a chat message in the chat schema.
  4. It publishes offer.made through StreamBridge. Spring Cloud Stream decides whether that goes to RabbitMQ or Kafka based on the active profile.
  5. The buyer gets 201 Created, and both people's open sockets receive the new offer on /topic/threads/{threadId}.
  6. The broker hands offer.made to the notification-service consumer group.
  7. Notification-service looks up the event's eventId in processed_event. If it is there, this is a redelivery and it stops.
  8. It writes an audit row to notification_log.
  9. It sends a push to the seller's FCM topic users-{uid}. If FCM fails, the failure is logged and the message is still acknowledged.

05 · Hosting and delivery

Running thirteen deployables for free

The free tiers are not just where Saryom runs. Their limits shaped real code: connection pools of three, a start-up cache, a daily keep-alive ping.

CI on every repo

GitHub Actions runs on pushes and pull requests to main. Backends run mvn -B verify on Temurin 25 (H2 for fast tests, Testcontainers 1.21.4 where real Postgres matters), then build the Docker image and prove the start-up cache loads (a test also checks the OTLP exporters are on the classpath) inside --memory=512m --cpus=0.1, the same box Render gives you. The web app runs lint, Vitest and a strict TypeScript build.

Deploys

Each repo has a render.yaml blueprint with autoDeploy: true, so merging to main ships that one service. Nothing deploys together, which is the point of separate repos and the AsyncAPI contract: a consumer must tolerate an older producer, so event changes are additive only.

06 · Observability · live since 21 Nov

Every request, traced into Grafana Cloud for free

All twelve Spring services now send metrics, traces and logs with OpenTelemetry to Grafana Cloud's free tier. One Render environment group switches it on everywhere. Full write-up: docs/observability.md in saryom-api-gateway.

Metrics → MimirMicrometer pushes once a minute: request rate, 5xx rate, latency, JVM heap and CPU, Hikari pool, log-line counts. Latency uses fixed buckets from 50 ms to 60 s instead of ~70 defaults, which keeps the whole system near 2k of the 10k free series. The 30 s and 60 s buckets exist because a cold start takes 35 to 75 s.
Traces → TempoMicrometer Tracing on the OpenTelemetry bridge. The gateway's X-Request-Id, returned to the browser, is stored as request.id, so an id from a bug report finds the whole request: { span.request.id = "…" }. Health checks and Spring Security filter spans are left out to save the allowance.
Logs → LokiAn OpenTelemetry Logback appender ships every line with its trace and span id, so you can jump from a slow span to its logs. Render's own log view still gets the same lines on stdout.
Switching it onOff unless OTLP_ENABLED=true. The Render env group saryom-observability holds OTLP_ENABLED, OTLP_ENDPOINT, OTLP_AUTH_HEADER and DEPLOY_ENV, linked to all twelve services. Locally, docker compose --profile observability up in saryom-db runs the same stack in one grafana/otel-lgtm container.

Traces cross the broker too.

In production the broker is RabbitMQ, and Spring Cloud Stream's Rabbit binder already carries the traceparent in message headers. So when chat-service publishes offer.made, the notification work that follows joins the same trace: section 03's whole offer flow shows up in Tempo as one trace, from the browser's tap to the FCM push. Locally, with Kafka (Redpanda), the same now holds: spring.cloud.stream.kafka.binder.enable-observation is on in the nine services that publish or consume (chat, housing, lending, listing, lostfound, meetup, notification, provider, user), so both brokers keep a request and its events in one trace. Still on the ideas list: JDBC query spans and Grafana Faro for browser errors.

07 · Known gaps

Worth a look

  1. Deploy blueprints have drifted from the live settings. A few render.yaml files still carry local-development settings that the Render dashboard overrides in production. Aligning the files with what actually runs is on the to-do list.
  2. Events can be lost. Publishing happens after the database write, and if the broker is unreachable the event is logged and dropped (the code says so honestly). For notifications that's acceptable. For listing.sold, a lost event means offers stay open on a sold item. A transactional outbox (write the event to a table in the same transaction, relay it afterwards) is the standard fix. The new SaryomErrorLogSpike alert will at least tell you when sends start failing.
  3. Twelve services on 750 free hours. Render's free tier gives 750 instance hours a month across the workspace. Twelve sleepy services fit only because most sleep most of the time. A busy month would need a paid instance or fewer, merged services.
  4. Mock fallback can hide an outage. The web app quietly switches to seeded demo data when a request hits a network error. That's great for demos, but a visitor during a real outage may see fake listings with no hint that something is wrong.
